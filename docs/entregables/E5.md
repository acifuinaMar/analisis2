## Introducción

Este documento especifica el contrato externo del sistema: la forma en que
los adaptadores primarios (API REST y, en el Proyecto Final, el servidor
MCP) exponen los casos de uso del núcleo diseñado en E3 e implementado en
E4. No se implementa ningún servidor HTTP en este entregable — pero el contrato queda
completamente especificado, validado y listo para implementarse.

Siguiendo la nota 8.2 del enunciado, el contrato **no se escribió dos
veces**: se definió una sola vez como esquemas `Zod` en
`src/contratos/`, y de ahí se generó automáticamente la especificación
OpenAPI.

```
src/contratos/
├── comun.ts             → Dinero, Error, Idempotencia (compartidos)
├── clientes.ts          → recurso Clientes
├── solicitudes.ts       → recurso Solicitudes
├── creditos.ts          → recurso Créditos (espejo de src/dominio)
├── pagos.ts             → recurso Pagos
├── cierres.ts           → recurso Cierres
├── cartera.ts           → recurso Cartera en riesgo
├── registro-rutas.ts    → arma el OpenAPIRegistry (18 rutas)
└── generar-openapi.ts   → genera docs/api/openapi.yaml

docs/api/openapi.yaml    → ARCHIVO GENERADO — no editar a mano
docs/adr/ADR-001-*.md    → estilo arquitectónico
docs/adr/ADR-002-*.md    → representación del dinero
```

Para regenerar el contrato tras modificar un esquema:

```bash
npm install
npm run contratos:openapi
```

El comando valida al compilar (TypeScript `strict`) y produce un
`docs/api/openapi.yaml` verificado con Swagger/OpenAPI 3.0.3 (validado con
`@apidevtools/swagger-parser` durante el desarrollo de este entregable).

## 2. Convención uniforme de manejo de errores

Toda respuesta de error (4xx/5xx) usa el mismo cuerpo, basado en RFC
9457 (*Problem Details*):

```json
{
  "codigo": "TRANSICION_INVALIDA",
  "mensaje": "El crédito 'CR-0001' está en estado 'solicitado' y no admite el evento 'registrarPago'.",
  "detalles": { "estado": "solicitado", "evento": "registrarPago" },
  "instancia": "req-8f21a3"
}
```

- **`codigo`** es estable y en mayúsculas: el cliente programa contra él.
Ejemplos: `VALIDACION`, `RECURSO_NO_ENCONTRADO`,
  `TRANSICION_INVALIDA`, `TASA_FUERA_DE_RAZONABILIDAD`.
- **Códigos de estado coherentes** con la causa:
  - `400 Bad Request` — falla de validación Zod (forma de la petición) o
    guarda la razón del dominio (por ejemplo: una tasa fuera del
    rango de la sección 6.3.1).
  - `404 Not Found` — el recurso no existe.
  - `409 Conflict` — la operación es válida en su forma, pero no para el
    estado actual del recurso: es exactamente el error
    `TransicionInvalida`.
- `detalles` es opcional y lleva contexto estructurado (por ejemplo: la lista
  de campos inválidos de un error de validación), nunca texto libre que
  haya que parsear.

## 3. Idempotencia en el registro de pagos

`POST /creditos/{id}/pagos` **exige** el encabezado `Idempotency-Key`
(UUID v4, ver `ClaveIdempotenciaEsquema` en `src/contratos/comun.ts`).

Comportamiento exigido por el contrato:

1. Primera vez que se ve la clave para ese crédito → se registra el pago,
   y se responde **`201 Created`** con el pago nuevo.
2. Reintento con la **misma** clave sobre el **mismo** crédito (por ejemplo 
   el cliente perdió la respuesta por un corte de red y reintenta) → se
   responde **`200 OK`** con el pago **ya existente**, sin volver a
   aplicar el pago ni a mover el saldo.

Esto cumple directamente el invariante de la sección 6.10: *"registrar
dos veces el mismo pago (misma clave de idempotencia) no altera el
saldo"*. La clave de idempotencia se guarda junto al pago (campo
`claveIdempotencia` en el esquema `Pago`).

Tomar en cuenta que esto es distinto de un pago insuficiente (sección 6.6.4): un
pago con clave nueva pero monto menor al adeudado **siempre se registra**
— nunca se rechaza por ser parcial. La idempotencia protege contra reintentos 
de la misma operación, no contra pagos incompletos.
